# Habez AI — аудит данных технолога и модели источников

25 сентября 2026. Режим: аудит → трассировка → отчёт. Данные, импорт,
характеристики и схема не менялись.

Повод: часть сведений о товарах владелец получил напрямую от технолога
завода, поэтому приложение №1 нельзя считать единственным источником
истины. Задача — найти эти сведения, установить происхождение каждого
значения и понять, как встроить несколько источников в слой знаний.

**О личных данных.** Репозиторий `habez-pro` публичный. Поэтому в этом
документе нет имени и почты технолога — только роль («главный технолог
завода»). Где они записаны — см. раздел «Безопасность».

## Sources

Реальные каналы, по которым сведения о товарах пришли в систему:

```
Письма главного технолога (.doc/.docx, иногда цифра в теле письма)
Паспорта качества, этикетки, маркировочные карточки — вложения тех же писем
          │  вручную, дословно, отдельным коммитом с описанием
          ▼
Приложение №1: products.json ◄── сайт завода habez-gips.ru (через «Habez сайт»)
          │                  ◄── страницы заводского каталога (снимки от владельца)
          │                  ◄── исходный каталог 31.08 (источник не записан)
          │
          │  • 04.09: снимок → api/src/db/legacy-products.json → seed (43 товара)
          │  • 08–12.09: разовые скрипты (в репозитории не сохранены),
          │    правило «брать только то, чего у нас меньше»
          ▼
Habez Pro: products.badges / spec_tables / sections / summary; variants
          │  npm run ai:import-specs
          ▼
AI-слой: ai_product_specs (origin = habez_internal, источник «Карточки товаров Habez Pro»)

Прайс завода 06.09 ──► Habez Pro (цены, ГКЛ и ПГП) ──► приложение №1 (07.09, без цен)
```

Итого в системе шесть независимых источников: письма технолога, паспорта
качества, этикетки, маркировочные карточки, заводской каталог, сайт
завода. Плюс прайс (коммерческий) и исходный каталог неизвестного
происхождения. В AI-слое сейчас все они слиты в **один** источник —
«Карточки товаров Habez Pro».

## Missing Provenance

1. **799 значений исходного каталога** — источник не записан ни в коммите,
   ни в заметках. Вероятно, заводской каталог или сайт, но это
   предположение. Нужен ответ владельца.
2. **Разовые скрипты переноса 8–12 сентября** в репозитории не сохранены.
   Что именно и по какому правилу они перенесли, восстановить можно только
   сравнением — как сделано выше.
3. **Оригиналы писем** на диске отсутствуют. Номер письма, дата и имя
   вложения есть только в сообщениях коммитов приложения №1.
4. **В AI-слое** у всех 726 характеристик один источник — «Карточки товаров
   Habez Pro». Письмо, паспорт или этикетка, из которых пришло значение, не
   записаны. Дата наблюдения — дата переноса (24.09), а не дата документа.
5. **`variants.per_pallet = 40` у 29 фасовок** придуман `seed.js` для любого
   мешка от 25 кг. Заводом количество на поддоне дано только для 6 товаров,
   и у них в `variants` оно верное. Покупатель видит «На паллете 40 шт» на
   витрине и в выгрузке для GitHub Pages.

## Current Schema Limitations

Может ли `ai_product_specs` хранить нужное:

| Что нужно | Сейчас | Мешает |
|---|---|---|
| Значение карточки + значение технолога + значение паспорта для одного свойства | **нет** | уникальный индекс `(tenant_id, product_id, spec_key)`: одно свойство — одна строка. Второе наблюдение вызывает конфликт 409 или перезаписывает первое |
| Разные значения от разных источников, если не совпадают | **нет** | та же уникальность; расхождение молча теряется (перенос выбирает одно, остальные в лучшем случае в отчёте) |
| Норма (declared) и фактический замер (measured) | **нет** | одно значение на запись; «фактически 50 %» сейчас отрезается разбором |
| Прочность 7 и 28 суток как разные свойства | **нет модели условий**; можно только завести разные ключи | нет поля условия (возраст, толщина слоя, операция, разбавление) |
| Значение конкурента | не для этой таблицы | `product_id` ссылается только на свои товары; конкуренты — фаза 3 |
| Гипотеза AI | да | `origin = ai_inference`, подтвердить нельзя |
| Разные фасовки одного товара | частично | есть `variant_id`, но в уникальный ключ он не входит: толщину 9,5 и 12,5 мм у ГКЛ одним ключом не записать |
| Кто передал и когда составлен документ | **нет** | нет полей `provided_by`, `document_date`, ссылки на документ |
| Уровень доступа источника | **нет** | ни у `ai_sources`, ни у записей нет `visibility` |

Для фактов (`ai_facts`, Phase 1) ограничений меньше: уникальность там
включает `source_id` и хеш значения, поэтому одно свойство из разных
источников уже может жить в нескольких записях. Это готовая основа.

## Proposed Evidence Model

Предложение, **не реализация**. Схема не менялась.

### Принцип: наблюдения отдельно, итог отдельно

```
ai_sources         — документ: письмо, паспорт, этикетка, каталог, сайт, карточка
   │
ai_facts           — наблюдение: «в паспорте X указано Y» (одно на источник)
   │  несколько наблюдений одного свойства сосуществуют
   ▼
ai_product_specs   — итоговое значение для сравнения
                     ссылается на выбранное наблюдение (fact_id)
                     + список альтернатив, если они расходятся
```

Для «Стандарта» это выглядело бы так:

```
наблюдение 1: 0,5 МПа             — ярлык карточки, исходный каталог 31.08
наблюдение 2: не менее 0,6 МПа    — таблица карточки, исходный каталог 31.08
наблюдение 3: (нет)               — паспорт качества не получен
итог:          нет — статус disputed, до решения владельца
```

### Поля provenance, которых не хватает

| Поле | Где | Зачем |
|---|---|---|
| `source_type` | есть в `ai_sources` | добавить значения: `technologist_letter`, `quality_passport`, `factory_label`, `marking_card`, `factory_catalog`, `factory_site`, `price_list`, `product_card` |
| `source_name` | есть (`name`) | «Паспорт качества на ГСП тип F» |
| `source_reference` | **нет** | номер письма, имя вложения, коммит приложения №1, страница каталога |
| `document_date` | **нет** | дата документа, а не дата переноса |
| `captured_at` | есть (`observed_at`) | когда внесено |
| `provided_by` | **нет** | роль, а не имя: «главный технолог завода», «владелец» |
| `verification_status` | есть | — |
| `original_value` | есть (`display_value`) | — |
| `normalized_value` | есть (`value_num`, `value_min/max`, `normalized_unit`) | — |
| `value_kind` | **нет** | `declared` / `measured` / `norm` — для паспортов |
| `condition` | **нет** | «7 суток», «при толщине 10 мм», «разбавление 1:9» |
| `supersedes` | есть у фактов | «0,3 вместо 0,5» — явная замена прежнего наблюдения |
| `notes` | частично (`parse_note`, `verify_note`) | — |
| `evidence_ref` | есть у фактов (`snapshot_ref`) | путь к скану или копии документа |
| `visibility` | **нет** | `public` / `internal` / `confidential` |

### Иерархия доказательности — только как предложение

Порядок ниже — **не назначенный приоритет**, а черновик для обсуждения.
Приоритет источников должен согласовать владелец бизнеса.

1. Официальный технический документ завода: паспорт качества, ТУ, ГОСТ
2. Письмо главного технолога с явным исправлением («вместо»)
3. Письмо главного технолога без исправления
4. Заводская этикетка, маркировочная карточка, заводской каталог
5. Внутренние данные, подтверждённые владельцем
6. Карточка товара в приложении №1 или Habez Pro
7. Сайт завода
8. Публичные источники третьих сторон
9. Вывод AI — никогда не факт

Открытые вопросы к этому порядку: этикетка против паспорта (ЛЮКС: «через 1
час» против 120 мин), свежее письмо против более раннего документа
(АКВАСТОП: 12 → 6 → 12). Правило «новее — значит вернее» здесь не работает
само по себе.
