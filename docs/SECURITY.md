# Безопасность: что сделано и что остаётся на вас

## Сделано в коде

**Пароли.** scrypt из стандартной библиотеки Node, у каждого пароля своя соль.
Сравнение — с постоянным временем. При входе пароль проверяется даже когда
пользователя нет: иначе по времени ответа можно было бы перебрать, какие адреса
зарегистрированы.

**Сессии.** Короткий access-токен (15 минут) живёт в памяти вкладки, а не в
localStorage — чужой скрипт на странице его не прочитает. Длинный refresh-токен
лежит в httpOnly-cookie, JavaScript до него не дотягивается, и в базе хранится
только его хеш: утечка базы не даёт войти в чужой аккаунт. При каждом обновлении
токен ротируется — старый гасится.

**Права.** Пять ролей со строгим порядком: покупатель → дилер → менеджер →
администратор → владелец. Все маршруты панели закрыты одним хуком на весь
модуль, а не проверками, расставленными по обработчикам, — забыть проверку
негде. Владельца не может изменить даже администратор.

**Разделение компаний.** Тенант определяется по домену на входе в запрос,
и каждый запрос к базе фильтруется по `tenant_id`. Подставить чужой
идентификатор через параметры нельзя: он не приходит от клиента.

**Ввод.** Все тела запросов проверяются схемами Zod: неописанное поле не дойдёт
до базы. Запросы к базе — только с подстановкой параметров, склейки строк с
пользовательским вводом нет нигде. Поисковый запрос экранируется перед
передачей в FTS5, иначе ввод стал бы синтаксисом запроса.

**Деньги.** Суммы считаются на сервере из прайса; то, что прислал клиент,
в расчёт не берётся. Хранятся в копейках целым числом — расхождений в копейку
на больших заказах не бывает. На платёж выдаётся ключ идемпотентности: двойное
нажатие не создаёт второй платёж. Вебхук ЮKassa не подписан, поэтому статус
меняется только после того, как сервер сам перезапросит платёж у ЮKassa.
Принимается только вебхук настроенного провайдера (`PAYMENT_PROVIDER`), платёж
ищется строго среди его платежей; демо-вебхук `mock` требует секретный ключ
платежа, а в production режим `mock` запрещён — сервер не стартует. Без
провайдера (`none`) маршрутов оплаты нет вовсе.

Дальше результат платежа применяется в одном месте (`applyPaymentResult`):
сумма из ответа провайдера сверяется с суммой платежа в базе (расхождение —
статус `mismatch`, заказ не трогается, менеджерам уведомление); второй
успешный платёж по уже оплаченному заказу помечается `needs_refund`, а не
оплачивает заказ повторно; пока у заказа есть незавершённый платёж, новый не
создаётся — отдаётся старая ссылка после перепроверки статуса у провайдера.
Создать платёж может только тот, кто вправе видеть заказ. Каждый переход
статуса платежа пишется в `payment_events`. Оформление заказа принимает
`Idempotency-Key`: повтор запроса возвращает тот же заказ и тот же токен.
Чек 54-ФЗ собирает `payments/receipt.js`: скидка распределяется по позициям,
доставка — отдельной строкой, сумма чека равна платежу копейка в копейку.

**Чужой заказ.** Право на заказ подтверждает сервер: вход владельца, роль
сотрудника или секретный токен, выданный один раз при оформлении и
хранящийся в базе хешем. Номер заказа и телефон правом доступа не являются —
их можно подобрать. Токен передаётся заголовком `x-order-token`, в адрес и
журналы не попадает.

**Журнал без персональных данных.** В журнал сервера не попадают тело
запроса, заголовки и cookies (pino их не пишет), а уведомления менеджерам
записываются только заголовком с номером заказа и результатом доставки —
имя, телефон, адрес и состав уходят лишь менеджерам (push, Telegram) и лежат
в базе. Телефон и почта в служебных записях маскируются, коды входа и ссылки
не записываются никогда (`lib/notify.js`, тест `notify-privacy.test.js`).

**Ограничение частоты.** 300 запросов в минуту на адрес, отдельные лимиты на
вход (10 за 5 минут), запрос кода (5 за 10 минут) и заявки (10 за 10 минут).
У кода из SMS свой счётчик попыток.

**Ошибки.** Наружу уходит текст на русском и идентификатор запроса. Стек,
SQL и внутренние подробности остаются в журнале сервера.

**Заголовки.** `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
в проде — HSTS. CORS разрешает только перечисленные адреса.

**Загрузка файлов.** Только jpg, png, webp, pdf; ограничение по размеру; имя
файла генерируется сервером — исходное имя из браузера не попадает в файловую
систему.

## Остаётся на стороне компании

1. **Свой `JWT_SECRET` в проде.** Сервер не запустится со значением по умолчанию —
   это сделано намеренно.
2. **Сменить демонстрационные пароли** сразу после установки.
3. **HTTPS обязателен.** Без него cookie сессии передаётся открыто.
4. **Резервные копии вне сервера** и проверка восстановления раз в квартал.
5. **152-ФЗ.** Хранятся телефоны, адреса, ИНН. Нужны политика обработки
   персональных данных, форма согласия при оформлении заказа, возможно —
   уведомление Роскомнадзора. Это юридическая работа, не техническая.
6. **Внешний аудит перед запуском.** Систему с персональными данными клиентов
   правильно показать специалисту по безопасности. Сертифицировать её мы не можем.
7. **Обновление зависимостей.** `npm audit` раз в месяц. Зависимостей намеренно
   мало — семь пакетов на сервере, три на витрине.

## Чего в системе нет

- Двухфакторной аутентификации для сотрудников — стоит добавить, когда в панели
  будет больше трёх человек.
- Шифрования персональных данных в самой базе. Защита строится на доступе к
  серверу; для заводского каталога это соразмерно, для системы с картами — нет.
- Защиты от подбора по распределённой сети адресов: лимиты считаются по адресу.
