## 2. Перенос (backfill)

Код: `api/src/ai/knowledge/reconciliation.js`, `evidence.js`
(`legacyObservationInput`), `legacy-provenance.js`.

Для каждой строки `ai_product_specs`:

| Поле наблюдения | Значение |
|---|---|
| `original_value`, `value_*`, `normalized_unit`, `comparator`, `parse_note`, `unit_raw` | из строки как есть, без повторного разбора |
| `source_type` | первоисточник из манифеста: `quality_passport` / `factory_technologist` / `factory_site` / `price_list`; иначе `unknown_legacy_origin`; `origin = ai_inference` → `ai_inference`; ручной ввод → `manual_entry` |
| `capture_channel`, `capture_ref` | `habez_pro_product_card`, `ai_sources#2 / spec_table / Технические характеристики / <подпись>` — если строка найдена в карточке |
| `upstream_ref`, `upstream_recorded_at` | `app1-commit-<hash>`, дата коммита (дата записи в №1, **не** дата документа) |
| `source_reference` | `app1-commit-<hash>` для известных, `habez-pro-spec#<id>` для неизвестных |
| `provided_at` | NULL: дата документа неизвестна |
| `captured_at` | `observed_at` строки — дата не меняется |
| `access_level`, `verification_status` | internal, unverified (D9) |
| `legacy_spec_id`, `legacy_origin` | ссылка на строку и её `origin` |
| `label` | подпись строки карточки (если найдена) |

Манифест — `docs/habez-ai-reconciliation-register.json` (реестр 2.2C). Сам
механизм в приложение №1 не ходит. Каждая запись манифеста сверяется со
строкой базы (номер, товар, ключ, значение). Любое расхождение — ошибка
плана, запись невозможна.

## 3. Идемпотентность

**Ключ записи** `backfill_key` — уникален в пределах компании (индекс
`ux_ai_obs_backfill`):

| Что | Формула ключа |
|---|---|
| старая строка | `legacy-spec:` + `ai_product_specs.id` |
| скрытая строка карточки | `card-row:` + `products.id` + `:` + вид (badge / spec_table) + `:` + заголовок таблицы + `:` + подпись |
| наблюдение плана | `plan:` + `REPAIRS[].id` (`plan:shov-adhesion` …) |
| история поддона | `pallet-default:` + `variants.id` |
| вопрос сверки | `item_key` (`D4:shov:adhesion_strength`, `AUTO:<slug>:<variant>:<ключ>:<условие>`), индекс `ux_ai_recon_item` |

Дополнительно `ux_ai_obs_legacy (tenant_id, legacy_spec_id)`: одна
строка — не больше одного наблюдения.

**Отпечаток содержания** `backfill_fingerprint` =
`sha256([product_id, variant_id, spec_key, condition_key, original_value,
source_type, source_reference])[0..24]`.

При повторном прогоне:

- ключ есть и отпечаток совпадает — строка «сохраняется», ничего не пишется;
- ключ есть, а отпечаток другой — ошибка плана («данные разошлись»),
  запись невозможна;
- исторические даты (`captured_at`) не переписываются, потому что
  существующие строки не обновляются вовсе;
- связей «заменяет» план не создаёт никогда (проверка до COMMIT);
- статус проверки перенос не меняет: только unverified, и только у новых
  строк.

Проверено: второй прогон — 0 вставок, 0 вопросов, 0 поддонов, 0 ошибок,
и на копии рабочей базы, и в тестах.

## 4. Транзакция и откат

| Требование | Как сделано |
|---|---|
| Прогон без записи | по умолчанию; рабочая база копируется (открывается только на чтение); на копии — миграция, план, запись, повторный прогон, откат; копия удаляется |
| Подтверждение | `--apply` требует `--confirm <отпечаток плана>`. Отпечаток учитывает вставки, поддоны, вопросы, манифест и содержимое таблиц. Изменилась база после прогона — запись отклоняется |
| Границы транзакции | R1–R6 — одна транзакция `BEGIN IMMEDIATE … COMMIT` |
| До и после | `counts` (12 счётчиков) и `fingerprint` (9 таблиц) до и после записываются в `ai_repair_runs` |
| Проверки до COMMIT (fail-fast) | `ai_product_specs`, `products`, `ai_facts`, `ai_sources` не изменились; связей не создано; новых наблюдений ровно по плану; вопросов ровно по плану; все новые — unverified и internal; очищено поддонов ровно по плану; в `variants` не изменилось ничего, кроме `per_pallet` 29 строк; 8 подтверждённых поддонов прежние. Любое нарушение — ROLLBACK |
| Копия базы | `VACUUM INTO <база>.pre-reconcile-<время>.db` перед записью |
| Журнал | `ai_repair_runs` (прогон, отпечаток плана, манифест, счётчики, отпечатки, копия, кто), `ai_repair_changes` (было / стало по каждой строке `variants`), `audit_log` (`ai.reconcile.apply`, `ai.reconcile.rollback`) |
| Откат | `--rollback <run_id>` одной транзакцией: вернуть `per_pallet`, если значение не трогали после прогона (иначе отказ); удалить участников, вопросы и наблюдения этого прогона. Отказ, если на них уже ссылаются связи или вопросы других прогонов. После — сверка отпечатков с состоянием «до» (иначе откат отменяется); статус `rolled_back` |
| Половинчатое состояние | невозможно: проверено искусственным сбоем посреди транзакции — отпечатки до и после совпадают, записи о прогоне нет |

Найдено и исправлено при проверке: в отпечаток таблицы `products` входили
`views` и `updated_at`. Их меняет сама витрина при каждом просмотре
карточки, и из-за этого подтверждённый план переставал бы совпадать, а
откат отказывал. Теперь `products` сравнивается только по содержательным
полям.

## 5. Старая проекция: наблюдения → «одно значение на ключ»

Код: `evidence-projection.js` (`projectResolution`, `makeEvidenceOverlay`).

| № | Правило |
|---|---|
| P1 | Значение есть, только если итог свойства `agreed` или `resolved_by_policy` **и** по ключу нет открытого вопроса сверки |
| P2 | Спор → числа `null`, `verificationStatus = disputed`, `displayValue` — все варианты через « / », `evidence.status = conflict` |
| P3 | Открытый вопрос (D2, D3, D4, D6, D10 …) → `unresolved`, числа `null` — даже если внутри свойства источники согласны |
| P4 | Несколько согласных источников → одно значение и **все** номера наблюдений; подпись — прежняя, если она среди согласных |
| P5 | Происхождение — `evidence.observationIds`, `evidence.openItems` |
| P6 | Наблюдений нет → `not_backfilled`, старое значение как есть |

Ответы на вопросы задачи:

1. Значение создаётся по P1.
2. NULL или unresolved — по P2 и P3.
3. Конфликт — P2.
4. Согласные источники — P4.
5. Происхождение — P5.
6. Конфликт не скрывается: числа пустые, в тексте все варианты.
7. Победитель не выбирается: ни по дате, ни по номеру, ни по порядку, ни
   по источнику.

**«Стандарт»:** `displayValue = "0,5 МПа / не менее 0,6 МПа"`, `value.num =
null`, `disputed`. В `/compare` число пустое, поэтому к сравнению по числам
значение не допускается (тест).

По прогону: 11 строк старого API в режиме evidence отдадут спор или вопрос
вместо одного числа — «Стандарт», ШОВ ×4, КОРОЕД, НАЛ, гидроизоляция,
АНТИПЛЕСЕНЬ, две краски.

## 7. Совместимость API

| Настройка | По умолчанию | Действие |
|---|---|---|
| `AI_EVIDENCE_ENABLED` | 0 | маршруты `/api/ai/observations*`, `/api/ai/products/:id/evidence` |
| `AI_EVIDENCE_READ_MODE` | `legacy` | `evidence` — старые маршруты отдают проекцию; действует **только** при `AI_EVIDENCE_ENABLED=1` |

- **legacy** — наложения нет вовсе, модуль проекции даже не загружается.
  Ответ побайтно прежний (тест сравнивает с `ai_product_specs`).
- **evidence** — те же поля тех же типов плюс блок `evidence` у каждой
  строки. В `/intelligence` дополнительно `evidence.scopedProperties`
  (свойства с условием или фасовкой) и `evidence.openItems`.
- Переключение в обе стороны — одной переменной, без миграции данных.
