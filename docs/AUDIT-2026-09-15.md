## 4. База данных

Схема: 20 таблиц, все бизнес-таблицы с `tenant_id`, внешние ключи включены
(`PRAGMA foreign_keys=ON`), WAL, `busy_timeout`. Индексы по всем рабочим
выборкам (заказы по статусу/пользователю, заявки, цены, корзины, FTS5).

**Связи проверены.** `products → categories (SET NULL)`, `variants → products
(CASCADE)`, `prices/stock → variants (CASCADE)`, `orders → users (SET NULL)`,
`order_items → orders (CASCADE)`, `order_items → variants (SET NULL)`,
`payments → orders`, `favorites → users/products`, `audit_log` без FK
(правильно — журнал переживает удаление актёра).

**Старые заказы при смене цены.** ✓ `order_items` хранит `product_name`,
`unit`, `qty`, `price`, `total` на момент заказа; `orders` — `subtotal`,
`discount`, `total`. Пересчёта по прайсу нигде нет.

**Удаление товара.** ✓ Через API товар не удаляется, а архивируется
(`status='archived'`). Прямое удаление в базе не сломает заказ: `variant_id`
станет NULL, название и цена останутся. Единственное — из `orderView`
пропадёт ссылка на карточку (её и так нет). Целостность: `PRAGMA
integrity_check` в копиях — `ok`.

## 7. Цены

Логика (`services/pricing.js`): уровень определяется на сервере
`tierFor(user)` из `users.price_tier` (fallback: `dealer` по роли). Для
уровня без своей цены берётся розница. Объёмные пороги — `min_qty`,
цена за штуку = минимум из подходящих порогов. Сроки действия
`valid_from/valid_to` учитываются. `amount=NULL` — «по запросу».

Проверено, что с фронта **нельзя** передать `price`, `discount`, `total`,
`role`, `dealerPrice`, `vipPrice`, `priceTier` ни в один маршрут: zod-схемы
`/api/orders`, `/api/cart/*`, `/api/account` таких полей не содержат, а
неизвестные поля zod отбрасывает. Роль и тариф меняются только через
`/api/admin/users/:id` (админ). Токен подписан, роль читается из базы.
Тест «дилер видит свою цену, розница — розничную» есть.

Единственная дыра в ценах — П-13 (позиции «по запросу» = 0 ₽ в заказе).

## 8. Остатки

**Сейчас остатки — справочные.** `stock.qty` показывается в карточке
(`inStock`), фильтр «в наличии» есть, менеджер задаёт `qty` руками.
При заказе, отмене, отгрузке остаток **не меняется**; `reserved` не
используется; отрицательных остатков быть не может (нет вычитания), но и
двое «последний мешок» закажут оба. Для текущего этапа (настоящих остатков от
завода нет, правило CLAUDE.md №1) это приемлемо и честно.

**Безопасная модель на будущее** (включается настройкой `trackStock: true`):

1. При создании заказа, в той же транзакции:
   `UPDATE stock SET reserved = reserved + :qty WHERE variant_id = :id AND qty - reserved >= :qty`
   — если `changes() = 0`, откатить заказ и ответить «осталось N».
   В SQLite это атомарно; при одном процессе гонки нет, при нескольких —
   защищает само условие в `UPDATE`.
2. `cancelled` → `reserved -= qty` (возврат в доступное).
3. `shipping`/`done` → `qty -= qty; reserved -= qty` (списание).
4. Ручное изменение `qty` менеджером — не трогает `reserved`.
5. Доступно к продаже = `qty - reserved`; это и показывать в карточке.
6. Все движения — в таблицу `stock_moves` (заказ, кто, сколько, когда) —
   без неё сверка с 1С невозможна.

## 12. Резервное копирование

**Сейчас.** `scripts/backup-db.sh`: `VACUUM INTO` (согласованная копия при
работающем сервере), `PRAGMA integrity_check`, подсчёт товаров/заказов,
хранится 30 последних, копирует `vapid.json`, папка в iCloud Drive.
Запускается перед каждой выкладкой; ежедневное расписание (plist) —
**не установлено** (требует действия владельца). Это хороший скрипт для Mac,
но **на сервере его нет**: в `DEPLOY.md` — cron с `.backup` и `find -delete`,
без проверки целостности, без выгрузки с сервера, без теста восстановления.

**Стратегия для сервера.**

1. Ежедневно 03:00 (`systemd timer`, не cron): `sqlite3 … "VACUUM INTO"` →
   `integrity_check` → если не `ok`, письмо/Telegram и выход с ошибкой.
2. Локально хранить 14 копий + `uploads` + `vapid.json` + `.env` (последний —
   в зашифрованном архиве, ключ у владельца).
3. **Удалённая копия**: тот же архив — в объектное хранилище (Яндекс Object
   Storage / Selectel, ~10 ₽/мес за такой объём) через `rclone`, с
   версионированием бакета и запретом удаления объектов (object lock) —
   это защита от случайного и злонамеренного удаления. Хранить 90 дней.
4. **Проверка, что копия создаётся**: `healthchecks.io` (бесплатно) — скрипт
   пингует URL после успеха; нет пинга сутки — письмо владельцу.
5. **Тест восстановления** — ежемесячно, автоматически: скрипт берёт
   последнюю копию, поднимает API на другом порту с `DATABASE_FILE=копия`,
   дёргает `/api/health` и `/api/catalog/products?limit=1`, сравнивает число
   товаров, гасит. Результат — в тот же healthchecks.
6. Копия iCloud с Mac владельца остаётся как третья, ручная линия.

Порядок восстановления описать в `DEPLOY.md` (стоп службы → подмена файла →
`npm run migrate` → старт → проверка) и **прогнать один раз до публикации**.

## 14. Развёртывание (production)

Что уже правильно в `DEPLOY.md`: systemd с `Restart=always`, nginx + certbot
(HTTPS), `X-Forwarded-*`, `COOKIE_SECURE=true`, `JWT_SECRET` обязателен,
миграции идемпотентны, health-check есть, CORS по списку доменов.

Рекомендации (в порядке важности):

1. **Сеть.** `HOST=127.0.0.1` в `.env`; ufw: открыты только 22, 80, 443.
   Без этого П-15 (`trustProxy`).
2. **Провайдер оплаты.** `PAYMENT_PROVIDER=none` до ЮKassa (П-41); `mock`
   запрещён при `NODE_ENV=production` (как пустой `JWT_SECRET`).
3. **Заголовки в nginx.** `Content-Security-Policy: default-src 'self';
   img-src 'self' data:; style-src 'self' 'unsafe-inline'; connect-src 'self'
   https://api.yookassa.ru; frame-ancestors 'none'` (инлайн-стилей у React
   много — `unsafe-inline` для стилей допустим); `Permissions-Policy`.
   `X-Frame-Options`/`nosniff`/`HSTS` приложение ставит само ✓.
4. **Кеш статики.** `location /assets/ { expires 1y; add_header Cache-Control
   "public, immutable"; }` — и для П-2.
5. **Rate limit на nginx** дополнительно к приложению: `limit_req` 10 r/s на
   `/api/auth/` — защищает и от П-15.
6. **Журналы.** pino → journald ✓. Настроить `journalctl` ротацию 14 дней;
   nginx `access.log` — 14 дней; в логах телефоны → не отдавать никому.
7. **Мониторинг.** UptimeRobot (бесплатно) на `https://…/api/health` раз в
   5 мин → SMS/почта владельцу. Healthchecks для копий (раздел 12).
   Место на диске — `df` в том же ежедневном скрипте, порог 80 %.
8. **Переменные окружения** — полный список для сервера: `NODE_ENV=production`,
   `HOST=127.0.0.1`, `PORT`, `PUBLIC_URL`, `WEB_URL`, `CORS_ORIGINS`,
   `JWT_SECRET`, `COOKIE_SECURE=true`, `PAYMENT_PROVIDER=none`,

## 17. Производительность

- Первый заход: 4 запроса (`meta`, `cart`, `refresh`, `products`), ~110 КБ
  JS сжато. Хорошо.
- Каталог: один запрос на список — `products` + подзапрос `price_from`,
  затем `decorate`: 3 запроса (фасовки, цены, фото) на всю страницу — не
  N+1 ✓. FTS5 для поиска ✓. ETag на `meta`, `Cache-Control` на списках ✓.
- Индексы: по всем фильтрам списка; `search_log` и `audit_log` без индекса
  по `query`/`action` — не критично.
- 56 товаров: ответ списка ~150 мс на localhost (замер по скриншотам
  сегодня). При 500 товарах — те же 3 запроса + пагинация на сервере уже
  есть (`page/limit ≤ 100`); узкое место — витрина без «показать ещё» (П-3).
  При 5 000 — SQLite справится (это десятки тысяч строк), но
  `SELECT MIN(pr.amount)` в подзапросе на каждую строку стоит заменить
  на JOIN с предагрегацией; `views = views + 1` на каждом просмотре — запись
  на чтение, при трафике перевести в батч.
- `newArrivals` в `meta` делает подзапрос `MIN(created_at)` — на большой
  таблице вычислять раз в час.
- Изображения: `media.url_webp` заполнен в сиде; ленивая загрузка `loading="lazy"` — проверить в `ProductCard` (в аудите не найдена явно) 🟢.

## 18. Масштабирование — ограничения архитектуры

| Рост | Ограничение | Что делать |
|---|---|---|
| 500+ товаров | П-3 (витрина), подзапросы цены | «Показать ещё», JOIN цен |
| 10 000+ пользователей | Панель «Пользователи» — 300 последних без поиска; `sessions` без чистки | пагинация + поиск, чистка (П-26) |
| Много заказов | Панель заказов с пагинацией ✓; `nextOrderNumber` через `COUNT(*) LIKE` — медленно на сотнях тысяч | счётчик в `tenants.settings` или `MAX(id)` |
| 1С | Нет внешнего API с ключом, нет `external_id` у товаров/заказов, нет движений остатков | раздел 19 |
| Telegram-бот | API готов (JSON, `x-tenant`), калькулятор и сравнение считаются на сервере ✓ | ключ доступа для бота (пока только Bearer пользователя) |
| Мобильный PWA | уже есть; серверная сборка — офлайн П-2 | |
| Несколько менеджеров одновременно | SQLite WAL: читатели не мешают, писатель один; `busy_timeout` 5 с. Для 5–10 менеджеров — с запасом. Нет защиты от «последний сохранивший затирает»: два менеджера открыли одну карточку — победит второй `PUT` | `updated_at` в `PUT` как версия: не совпала → 409 «карточку уже изменили» |
| Несколько процессов Node (кластер) | Синхронный SQLite и отсутствие блокировок на уровне заказа — гонки в заказе/остатке станут возможны | не запускать более одного процесса; при росте — Postgres по `DEPLOY.md` |

Главный архитектурный факт: **один процесс + SQLite** — это осознанный выбор,
и до нескольких тысяч заказов в месяц он не будет узким местом.
