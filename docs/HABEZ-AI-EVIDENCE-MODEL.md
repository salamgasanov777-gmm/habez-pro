## 1. Что было не так

`ai_product_specs` хранит **одно значение на свойство товара**: уникальный
индекс `(tenant_id, product_id, spec_key)`.

| Ограничение | Что из-за него терялось |
|---|---|
| одно свойство — одна строка | значения карточки, технолога и паспорта не могли лежать рядом; второе давало 409 или затирало первое |
| нет условия | прочность за 7 и за 28 суток, расход при слое 1 и 10 мм не различались |
| нет declared / measured / norm | «50–57 % (фактически 50 %)» теряет замер |
| `variant_id` не в ключе | толщины 9,5 и 12,5 мм одного ГКЛ одним ключом не записать |
| бедное происхождение | у всех 726 записей источник — «Карточки товаров Habez Pro», дата — дата переноса |
| нет уровня доступа | AI не отличил бы публичное от внутреннего |

## 2. Модель

```
products / variants            (каталог, не меняется)
   │
   ├─ свойство = товар × фасовка × ключ × условие
   │     │
   │     └─ ai_spec_observations      наблюдение: «источник X утверждает Y при условии Z»
   │            │   несколько на одно свойство, ни одно не затирает другое
   │            ├─ source_type, source_reference, provided_by, provided_at …  (происхождение)
   │            └─ ai_observation_relations   «B заменяет A», «B подтверждает A» …
   │
   └─ ai_product_specs            прежняя «итоговая» строка; не меняется, на ней работают старые /api/ai/*
```

Почему отдельная таблица, а не `ai_facts` (так предлагал аудит). В `ai_facts`
нет диапазона (`value_min`/`value_max`), признака границы («не менее»),
фасовки и условия, а объект указывается полиморфно (`subject_type` +
`subject_id`, свойство — свободной строкой `attribute`). Пришлось бы добавить
больше полей, чем там уже есть, и смешать общие факты о рынке с
характеристиками товара. `ai_facts` остаётся для фактов о компаниях, ценах и
рынке, как и задумано в фазе 1.

### Термины

| Термин | Что это | Где |
|---|---|---|
| **Наблюдение** (observation) | одно утверждение одного источника о значении свойства: «письмо технолога от 05.09 утверждает: прочность сцепления не менее 0,3 МПа в возрасте 7 суток» | строка `ai_spec_observations` |
| **Свойство** (property) | товар × фасовка × ключ словаря × условие. Наблюдения одного свойства сравниваются между собой | группа в `GET /api/ai/products/:id/evidence` |
| **Источник** (source) | вид доказательства (`source_type`) и ссылка на конкретный документ (`source_reference`); по желанию — ссылка на карточку `ai_sources` (`source_id`) | поля наблюдения |
| **Доказательство** (evidence) | то, на чём держится наблюдение: вид источника, ссылка, дата документа, роль передавшего, цитата (`evidence_note`), путь к скану (`evidence_ref`, пока пусто) | поля наблюдения |
| **Происхождение** (provenance) | весь набор полей выше плюс `captured_at` — когда внесено | поля наблюдения |
| **Проверка** (verification) | подтвердил ли человек, что источник говорит именно это: `unverified → verified / disputed / stale / rejected`, переходы как в фазе 1 | `verification_status` |
| **Замена** (replacement) | источник сам пишет, что новое значение идёт «вместо» старого. Это **связь** между двумя наблюдениями, а не удаление старого | `ai_observation_relations.relation_type = 'replaces'` |
| **Заменённое** (superseded) | наблюдение, на которое указывает связь «заменяет». Строка остаётся, в выборе значения не участвует, видна в истории | `lifecycle_status = 'superseded'` |
| **Условие** (condition) | при чём верно значение: возраст, толщина слоя, «на мешок», температура, разбавление | `conditions_json` + `condition_key` |
| **Фасовка** (variant) | конкретный `variants.id` (он же SKU) | `variant_id` |
| **Тип утверждения** | declared / measured / norm / instruction / replacement / unknown | `statement_type` |
| **Уровень доступа** | public / internal / confidential | `access_level` |

### Вид источника (`source_type`)

`product_card` · `factory_technologist` · `technical_document` ·
`quality_passport` · `label` · `marking_card` · `factory_catalog` ·
`price_list` · `measurement` · `manual_entry` · `public_source` ·
`generated_default` · `ai_inference`.

`manual_entry` — запись, внесённая вручную в панели без указания
документа. Нужен для переноса старых ручных записей, чтобы не выдавать их
за «карточку товара».

Список **не упорядочен по доверию**. `generated_default` добавлен для
значений, которые подставила программа (например `per_pallet = 40` из
`seed.js`). `generated_default` и `ai_inference` **никогда** не становятся
`verified`: подтверждённое значение заводится отдельным наблюдением с
настоящим источником.

Поле `ai_sources.source_type` (8 каналов фазы 1: сайт производителя, дилер,
маркетплейс…) не меняется. Это другая классификация: канал, по которому
пришли сведения, а не вид документа.

### Тип утверждения (`statement_type`)

| Тип | Когда ставится | Пример |
|---|---|---|
| `declared` | производитель заявляет значение | «не менее 2,5 МПа» в письме технолога |
| `measured` | фактический замер | «фактически 50 %» в паспорте |
| `norm` | нормативное значение | «норма по ГОСТ — 550 Н» |
| `instruction` | технологическое условие работы | «5–7 литров воды на 1 мешок» |
| `replacement` | источник сам говорит «вместо» | «0,3 МПа вместо 0,5» |
| `unknown` | из текста не следует ничего из перечисленного | все 726 перенесённых из карточек |

Тип ставит человек (или план исправлений), а не разбор строки: из «2 МПа»
не видно, заявлено это или замерено.

**Заявленное, замер и норма не спорят друг с другом.** Итог по свойству
считается раздельно: `current` (declared, replacement, instruction, unknown),
`measured`, `norm`. «50–57 %» и «фактически 50 %» — оба верны. Это проверено
тестом.

### Условия

Закрытый список ключей, чтобы «7 сут», «7 суток» и «неделя» не стали тремя
разными условиями:

| Ключ | Смысл | Тип |
|---|---|---|
| `age_days` | возраст материала, сут | число |
| `layer_mm` | толщина слоя, мм | число |
| `temperature_c` | температура, °C | число |
| `layers` | число слоёв | число |
| `per` | на единицу: `kg`, `bag`, `m2`, `l` | текст |
| `pack` | фасовка текстом, если её нет в `variants` | текст |
| `dilution` | разбавление, «1:9» | текст |
| `substrate` | основание | текст |
| `note` | прочее, подтверждённое источником | текст |

**Условие принимается только с дословной цитатой** (`condition_text`):
без неё сервер отвечает 400. Условие из воздуха — такое же выдуманное
значение.

`conditions_json` — разобранное: `{"age_days": 7}`. `condition_key` —
каноническая строка `age_days=7` (ключи по алфавиту, текст в нижнем
регистре). `condition_text` — как написано в источнике: «в возрасте 7 сут».

Условие **не** превращается в отдельное свойство: прочность за 7 и за 28
суток — это `compressive_strength` с разными условиями, а не два ключа.
Условия не выводятся из текста автоматически: их задаёт человек или план
исправлений.

### Фасовки и SKU

`variant_id` участвует в группировке. Гипсокартон 9,5 и 12,5 мм — две
группы одного ключа, и спора между ними нет (тест с 63 и 51 листом на
поддоне). У каждой фасовки свой `variants.sku`, поэтому SKU отдельно не
хранится: он берётся из `variants`.

Кроме ключей словаря (`spec-dictionary.js`, 72 ключа) наблюдения принимают
три фасовочных ключа: `per_pallet`, `gtin`, `ntin`. В `ai_product_specs` их
по-прежнему нет, они живут в `variants`. Но о них нужны сведения с
доказательствами: «40 на поддоне» из `seed.js` и «63 листа» из карточки
весят по-разному. Для фасовочного ключа `variant_id` обязателен. Штрихкод
хранится строкой, а не числом.

### Связи

| Тип | Смысл | Что делает |
|---|---|---|
| `replaces` | B заменяет A | A → `superseded`; строка A остаётся |
| `conflicts_with` | B противоречит A | только запись |
| `confirms` | B подтверждает A | только запись |
| `clarifies` | B уточняет A (например, добавляет условие) | только запись |

Основание связи (`basis`): `explicit_source_statement` — источник говорит
сам, нужна цитата или ссылка; `user_decision` — решил владелец. Связывать
можно только наблюдения одного товара, в том числе через разные ключи (у
ШОВа старое «время схватывания» заменено «началом схватывания»). Круг из
замен запрещён, заменённое наблюдение не может заменять другое, повтор
связи — 409. Создаёт связи только администратор.

Замена между разными ключами — только `user_decision` (R8).

Снятие связи пока не реализовано: чтобы вернуть заменённое, нужна новая
связь с основанием `user_decision`. Это сделано намеренно, чтобы история не
переписывалась.

### Выбор действующего значения — формальные правила

Код: `resolveGroup()` в `api/src/ai/knowledge/evidence.js`. Тесты:
`api/test/ai-evidence-gate.test.js`.

| № | Правило |
|---|---|
| R1 | Свойство — это товар × фасовка × ключ × условие. Внутри свойства — три класса утверждений: `current` (declared, replacement, instruction, unknown), `measured`, `norm`. Разные свойства и разные классы между собой не спорят |
| R2 | Кандидат — наблюдение `active` со статусом не `rejected`. `superseded` и `withdrawn` в выборе не участвуют, но видны в `history` |
| R3 | Два значения равны, если совпадают число, границы и логическое значение, единица и **признак границы**. Для текста — строка без учёта регистра. «0,3 МПа» и «не менее 0,3 МПа» — разные |
| R4 | Все кандидаты равны → `agreed`. Итог — само значение (числа, единица, все варианты написания) и список **всех** подтверждающих наблюдений. Одно «главное» наблюдение не выбирается |
| R5 | Кандидаты расходятся → `resolved_by_policy`, только если владелец задал приоритет для **каждого** участвующего вида источника и все наблюдения лучшего вида согласны; проигравшее значение показывается в `overruled`. Иначе → `pending_user_decision`, `value = null`, варианты упорядочены по значению |
| R6 | Победителя **не** определяют: дата документа, дата записи, номер записи, порядок вставки, вид источника без утверждённого приоритета, `extraction_confidence`, статус проверки |
| R7 | Тип `replacement` сам ничего не заменяет. Заменяет только связь `replaces`. Наблюдение `replacement` без такой связи попадает в `unlinkedReplacementClaims` — это сигнал человеку |
| R8 | Связь `replaces` между **разными** ключами — только с основанием `user_decision`. «Старое свойство и новое — одно и то же» источник не утверждает никогда, это решение человека |

Ответы на вопросы аудита:

1. Несколько наблюдений одного свойства — да, без ограничения. Одинаковое
   утверждение из того же документа отклоняется (409).
2. Активное — `lifecycle_status = active` и статус не `rejected` (R2).
3. Два разных значения → `pending_user_decision`, значения нет (R5).
4. Тип `replacement` без связи → ничего не заменяет, виден как сигнал (R7).
5. Заменённое — `superseded` через связь, строка не удаляется и не
   меняется (тест).
6. Таблица приоритетов пустая → любое расхождение — `pending_user_decision`.
7. API наблюдений конфликт одним значением не возвращает. **Старый путь
   возвращает:** `/api/ai/specs`, `/intelligence`, `/compare` читают
   `ai_product_specs`, где спор уже «решён» при переносе правилом «таблица
   важнее ярлыка» («Стандарт»: 0,6 МПа, а 0,5 МПа ярлыка отброшено). См.
   раздел 8.1.

### Происхождение и приватность

| Поле | Что хранится |
|---|---|
| `source_type` | вид доказательства |
| `source_name` | «Письмо главного технолога завода от 05.09.2026» |
| `source_reference` | безопасный идентификатор: `technologist-note-2026-09-05`, `habez-pro-card/badge/ярлык карточки` |
| `captured_at` | когда внесено в систему |
| `provided_at` | дата документа |
| `provided_by` | **только роль**: `factory_technologist`, `factory_management`, `factory_laboratory`, `owner`, `sales_manager`, `dealer`, `unknown` |
| `original_value` | исходная строка, всегда |
| `value_*`, `normalized_unit`, `comparator` | разобранное значение |
| `verification_status`, `verified_by`, `verified_at`, `checked_at`, `verify_note` | проверка |
| `extraction_confidence` | точность прочтения, не доверие к источнику |
| `evidence_note` | цитата или пояснение |
| `evidence_ref` | путь к скану (пока пусто, решение №13) |
| `access_level` | public / internal / confidential |

Почта и телефон не принимаются ни в одном свободном поле происхождения
(`source_name`, `source_reference`, `evidence_note`, `evidence_ref`,
`condition_text`, `label`, `verify_note`, `basis_note`, `original_value`) и
в источниках фазы 1 (`name`, `url`, `publisher`, `description`): сервер
отвечает 400.
В `provided_by` можно указать только роль из списка, имя не пройдёт. В плане
исправлений, в этом документе и в коде нет ни имени, ни почты технолога.

### Уровень доступа

| Уровень | Кто видит |
|---|---|
| `public` | менеджер и выше; значение уже опубликовано в карточке |
| `internal` | менеджер и выше (по умолчанию) |
| `confidential` | только администратор и владелец; заводит только администратор |

Итог по свойству считается по **всем** наблюдениям, в том числе
конфиденциальным. Менеджеру конфиденциальные значения, номера и ссылки не
показываются, но спор остаётся спором: вариант виден как `{hidden: true}`.
Иначе менеджер видел бы «согласно» там, где конфиденциальный замер
противоречит. Связи показываются, только если оба их конца видны роли.
Свойство, где всё конфиденциально, менеджеру не показывается вовсе.

Гость — 401, покупатель и дилер — 403 на всех маршрутах наблюдений.
Покупательский API (`/api/catalog/*`) таблицы наблюдений не читает.

### Правило публикации

Функция `publicationDecision()` в `evidence-model.js`. Наблюдение может
попасть покупателю, только если выполнены **все** условия:

1. `access_level = public`;
2. вид источника не `generated_default` и не `ai_inference`;
3. `verification_status = verified`;
4. `lifecycle_status = active`;
5. итог свойства `agreed` или `resolved_by_policy`;
6. наблюдение среди подтверждающих этот итог.

Сейчас витрина наблюдения не читает вообще, правило закреплено тестами на
будущее. По прогону на копии: публикуемых 0 из 760 (731 не проверены,
29 подставлены программой).

### Два понятия, которые нельзя смешивать

| Понятие | Где | Что значит | Участвует в выборе значения |
|---|---|---|---|
| Доверие к виду источника | `ai_source_type_priorities` (пустая) | насколько владелец доверяет паспорту против карточки | только если задано для всех участников (R5) |
| `extraction_confidence` | наблюдение, 0–100 или пусто | насколько точно значение прочитано из **этого** документа | **нет** (R6) |
| `interpretation` | план исправлений | следует ли сама правка из текста дословно (`explicit`) или частично (`partial`) | не хранится в базе |
| `trust_base` | `ai_sources` (фаза 1) | базовое доверие к каналу | не используется наблюдениями |
| `confidence` | `ai_product_specs` (фаза 2) | было выставлено по `origin` (95 у всех 726) — это доверие к происхождению | в наблюдения **не** копируется, доступно по `legacy_spec_id` |

## 3. Миграция `2026-09-ai-evidence`

### Текущая схема (не меняется)

`ai_sources`, `ai_facts` (фаза 1), `ai_product_specs` (фаза 2) — как в
[HABEZ-AI-ARCHITECTURE.md](HABEZ-AI-ARCHITECTURE.md), разделы 14-bis и 14-ter.
Уникальный индекс `ux_ai_specs (tenant_id, product_id, spec_key)` **остаётся**:
на нём держится сравнение `/api/ai/products/compare`, где на товар и ключ
нужно ровно одно число.

### Новая схема (только добавление)

Файл `api/src/ai/knowledge/evidence-schema.sql`:

- `ai_spec_observations` — поля выше. Уникальность `(tenant_id,
  content_hash)`. Хеш считается от товара, фасовки, ключа, условия, типа
  утверждения, вида и ссылки источника и исходной строки. Тот же документ с
  тем же значением второй раз не записывается, всё остальное может
  совпадать. Индексы: по свойству, по источнику, по статусу, по
  `legacy_spec_id`.
- `ai_observation_relations` — `from`, `to`, `relation_type`, `basis`,
  `basis_note`, `source_reference`, `created_by`, `created_at`;
  `CHECK (from <> to)`, уникальность `(tenant, from, to, type)`.
- `ai_source_type_priorities` — `(tenant_id, source_type)` → `priority`,
  кто и когда решил. Пустая.

`ALTER TABLE` не используется, существующие таблицы не меняются.

### Обратная совместимость

| Что | Состояние |

### Перенос 726 записей (подготовлен, не выполнен)

`backfillFromSpecs()` делает из каждой строки `ai_product_specs` наблюдение
с **теми же** исходной строкой, числами, единицей, признаком границы,
заметкой разбора, фасовкой, проверкой (`verified_by`, `verified_at`,
`checked_at`), источником, автором и датой внесения
(`captured_at = observed_at`), плюс `legacy_origin` и ссылка
`legacy_spec_id`. Значение заново не разбирается. Повторный запуск ничего
не дублирует.

Вид источника — по происхождению строки: ярлык или таблица карточки →
`product_card` / `public`; `origin = ai_inference` → `ai_inference`
(вывод модели не «отмывается» в карточку); ручной ввод → `manual_entry` /
`internal`.

Что **намеренно** не копируется: `confidence` (95 у всех — это доверие к
происхождению, а не точность прочтения) и дата документа. Дата документа
(`provided_at`) у значений карточки неизвестна: исходный каталог 31.08 без
источника, ярлыки — без даты. Дата переноса в неё **не** подставляется, она
остаётся в `captured_at`. Условий у старых строк нет: где возраст или
толщина зашиты в ключ (`compressive_strength_28d`, `consumption_per_mm`),
они сохраняются в самом ключе.

На копии: 726 из 726, расхождений по 17 полям — 0, все 726 —
`product_card/public`, `provided_at` пуст у всех.

**Расхождение двух хранилищ.** `ai:import-specs` и `PATCH /api/ai/specs/:id`
пишут только в `ai_product_specs`. После переноса строка и её наблюдение
могут разойтись. `legacyDrift()` находит такие пары и строки без
наблюдения. Прогон печатает счётчик, тест проверяет, что правка через
старый API обнаруживается, а наблюдение само не переписывается.

`/api/ai/products/:id/evidence`. **Ответа AI нет вообще**: модели, чата и
выдачи для него в проекте нет (фаза 5). То есть модель наблюдений сейчас
**параллельное хранилище**, а не рабочий источник: ни один существующий
экран и ни один существующий маршрут её не читает. Это ожидаемо для фазы
2.2B, но это нужно назвать прямо.

**Путь «товар → характеристики → сравнение → API/UI»** целиком идёт через
`ai_product_specs`. Он возвращает спор одним значением: «Стандарт»
отдаётся как 0,6 МПа, потому что при переносе таблица важнее ярлыка. Это
правило записано в коде, но не утверждено владельцем.

### 8.2 Canonical: что станет источником для AI

| Критерий | A. `ai_product_specs` | B. наблюдения | C. переходная гибридная |
|---|---|---|---|
| Выдача (retrieval) | одно значение, без условий и фасовок | все утверждения с условием, фасовкой и уровнем доступа | AI читает наблюдения; старые экраны — проекцию |
| Сравнение | готово, но «побеждает» таблица | только по `agreed`/`resolved_by_policy` одной фасовки и условия; споры исключаются явно | сравнение переписывается на итог наблюдений |
| Поиск конфликтов | невозможен: второе значение не хранится | встроен (`pending_user_decision`) | из наблюдений |
| Ссылки на источник (citations) | один источник на всё, без даты документа | вид, ссылка, дата, роль, цитата | из наблюдений |
| Ответы AI | может уверенно назвать спорное значение | может сказать «источники расходятся: …» | из наблюдений |
| Миграция | не нужна | перенос 726 + переписать чтение | перенос 726, чтение переводится по одному месту из 8.1 |

**Вывод: canonical для AI — B, наблюдения. Путь к нему — C.**

- `ai_product_specs` превращается в **производную проекцию**: одна строка
  на товар и ключ, которая в будущем строится из итога наблюдений
  (`agreed` или `resolved_by_policy`, без условия и фасовки). Спорное
  свойство в проекции помечается, а не «решается».
- До переключения писатели старого пути (`import-specs`, `updateSpec`)
  продолжают работать. Расхождение ловит `legacyDrift()`. Двух равноправных
  источников истины нет: для AI — наблюдения, для старых экранов — проекция
  с известным отставанием.
- Выбор A оставил бы AI без конфликтов и без происхождения. Это прямо
  противоречит правилу «цены и данные не выдумывать».

### 8.3 Проверка условия «7 суток» (ШОВ)

Основание найдено, это не вывод модели. В приложении №1 карточка ШОВа
переписана коммитом `1e43732` от 05.09.2026 («карточка переписана по
документу технолога»):

| | До коммита | После коммита |
|---|---|---|
| ярлык | «Прочность на отрыв» — 0,5 МПа | «Прочность на отрыв, 7 сут» — не менее 0,3 МПа |
| таблица | «Адгезия (прочность на отрыв)» — не менее 0,5 МПа | «Прочность сцепления раствора с основанием **в возрасте 7 сут**» — не менее 0,3 МПа |

Возраст стоит дословно в подписи строки. Оригинала письма на диске нет:
это запись со слов документа, а не скан. Поэтому условие хранится вместе с
дословной цитатой подписи (`condition_text`), а сервер теперь не принимает
условие без цитаты. Старые 0,5 МПа возраста не имели; «вместо» — в записи
коммита. Связь «заменяет» оставлена: ключ тот же, `explicit_source_statement`
со ссылкой на место записи.

### 8.4 Проверка «время схватывания → начало схватывания»

- Словарь: `setting_time` — «Время схватывания», `setting_time_start` —
  «Начало схватывания». Это **разные ключи**. Время схватывания в ГОСТ
  описывается началом и концом.
- В карточке до коммита — только ярлык «Время схватывания 60 мин», строки
  таблицы не было. После — «Начало схватывания, не ранее 70 мин».
- Запись коммита: «начало схватывания (70 мин вместо 60)». То, что старые
  60 мин были именно **началом** схватывания, утверждает автор записи, а не
  дословный текст документа.

Ответ: 1) доказательно одно и то же свойство — **нет**; 2) по словарю это
два свойства; 3) в прошлом прогоне это было не нормализацией, а связью
между ключами; 4) при такой связи смысл старого `setting_time` потерялся
бы. **Исправлено:** связь убрана из плана. Замена между разными ключами
теперь возможна только с основанием `user_decision` (R8, тест). Старое
«60 мин» остаётся действующим, новое наблюдение помечено как «вместо без
связи».

### 8.5 Фасовка и упаковка

| Уровень | Как хранится | Проверено |

### 8.6 Что найдено и что сделано

**Реальные проблемы, исправленные в коде (данные не менялись):**

1. Итог «согласно» выбирал одно наблюдение-«представителя» по статусу
   проверки, а при равенстве — по порядку вставки. Теперь итог — само
   значение и все подтверждающие (R4).
2. Признак границы не учитывался: «0,3» и «не менее 0,3» считались
   согласием. Теперь это спор (R3).
3. `confidence` при переносе получал 95 из `origin`, то есть доверие к
   происхождению. Поле заменено на `extraction_confidence` (по умолчанию
   пусто) и в выборе не участвует. В плане исправлений «high/medium» заменено
   на `interpretation` (`explicit` / `partial`).
4. Замена `setting_time → setting_time_start` делалась без доказательства
   тождества ключей. Убрана, добавлено правило R8.
5. Условие можно было задать без цитаты. Теперь цитата обязательна.
6. КОРОЕД привязывался к фасовке «мешок 25 кг» без основания в тексте.
   Убрано.
7. Менеджер видел итог только по видимым ему наблюдениям: скрытый
   конфиденциальный спор превращался в «согласно». Теперь итог считается по
   всем наблюдениям, конфиденциальные варианты скрыты (`hidden: true`).
8. Связь с конфиденциальным наблюдением была видна менеджеру (номер). Теперь
   связь видна, только если видны оба конца.
9. Перенос записывал **любую** старую строку как `product_card`, в том
   числе вывод модели (`origin = ai_inference`) и ручной ввод. Теперь вид
   источника берётся по происхождению.
10. При переносе терялись `checked_at`, `created_by`, `origin`. Теперь
    сохраняются.
11. Источники фазы 1 (`ai_sources`) принимали почту и телефон в названии и
    издателе. Теперь 400.
12. Новый путь нельзя было включить отдельно от старого. Добавлен
    переключатель `AI_EVIDENCE_ENABLED` (по умолчанию выключен).
13. Не было способа заметить расхождение хранилищ после переноса. Добавлен
    `legacyDrift()`.
14. Правила публикации не было. Добавлено `publicationDecision()` с тестами.

**Только потенциальные (сейчас вреда нет):**
