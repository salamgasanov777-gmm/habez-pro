# HGZ Pro — платформа каталога и заказов для производителя стройматериалов

Переработанная версия каталога Хабезского гипсового завода: те же 43 товара и
688 строк заводских характеристик, но вокруг них — сервер, база, вход, корзина,
заказы, оплата и панель управления.

Система **мультитенантная**: одна установка обслуживает несколько заводов или
дилеров. У каждого свой домен, каталог, цены, менеджеры и клиенты; данные
компаний не пересекаются. Подключение второй компании — запись в таблице
`tenants`, а не новая разработка.

---

## Что умеет

**Витрина (PWA)**
- Каталог: разделы, поиск по названию, ГОСТу и тексту карточки (FTS5), подбор по задаче
- Карточка: показатели, разделы инструкции, таблицы характеристик, документы
- Калькулятор расхода — считает сервер, одна формула на сайт, приложение и бота
- Сравнение товаров сводной таблицей
- Избранное — в браузере у гостя, на сервере после входа
- Корзина у гостя без регистрации, переезжает на аккаунт при входе
- Оформление заказа, промокоды, самовывоз или доставка
- Оплата картой; позиции без цены уходят заявкой менеджеру
- Тёмная тема, офлайн-режим, установка на телефон значком

**Кабинет клиента** — заказы со статусами, повторная оплата, профиль, дилерские цены.

**Панель управления**
- Сводка: заказы, выручка, состояние каталога, что смотрят, **что искали и не нашли**
- Товары: редактор карточки, показатели, разделы, таблицы, калькулятор, SEO
- Цены: розница, дилер, VIP, объёмные пороги, массовое изменение процентом
- Остатки, заказы со статусами и историей, заявки, пользователи и роли
- Настройки компании и оформления, журнал изменений, выгрузка прайса в CSV для Excel

**API** — REST, документирован в `/api/openapi.json`. Через него работают
сайт, PWA и любой будущий клиент: телеграм-бот, 1С, мобильное приложение.

## Устройство

```
HGZ_pro/
├── api/                      Node.js 22+ · Fastify · SQLite (node:sqlite)
│   ├── src/
│   │   ├── config.js         все настройки в одном месте
│   │   ├── server.js         сборка приложения, обработка ошибок, заголовки
│   │   ├── db/               схема, миграции, перенос каталога из products.json
│   │   ├── lib/              пароли, JWT, деньги, уведомления
│   │   ├── plugins/          тенант, аутентификация
│   │   ├── routes/           каталог, корзина, заказы, оплата, заявки, админка
│   │   ├── services/         цены, каталог, корзина, заказы
│   │   └── payments/         mock (демо) и ЮKassa
│   └── test/smoke.test.js    сквозной тест: каталог → заказ → оплата → статус
└── web/                      React 18 · Vite · без UI-библиотек
    ├── public/               иконки, манифест, service worker, фото товаров
    └── src/
        ├── styles/app.css    вся система оформления
        ├── components/       шапка, карточка, модальные окна, иконки
        ├── pages/            витрина, товар, корзина, оформление, кабинет
        └── admin/            панель управления (отдельным чанком)
```

**Почему так**

- *SQLite вместо Postgres.* Каталог завода — это десятки тысяч строк, а не
  миллионы. Встроенный в Node драйвер снимает целый класс проблем: нечего
  устанавливать, нечего администрировать, резервная копия — это копирование
  одного файла. Переход на Postgres описан в `DEPLOY.md` и не затрагивает
  бизнес-логику: весь SQL собран в `services/` и `routes/`.
- *Прямой SQL вместо ORM.* Запросов немного, они простые и читаются целиком.
- *React без UI-библиотек.* Витрина весит 71 КБ в сжатом виде и открывается
  на телефоне в поле, где интернет — это одна палка EDGE.
- *Криптография на стандартной библиотеке.* Пароли — scrypt, токены — HMAC,
  никаких сторонних пакетов там, где утечка зависимости означает утечку паролей.

## Две сборки одного приложения

Приложение собирается в двух видах из одного и того же кода.

**С сервером** — всё, что описано выше: заказы, оплата, кабинет, панель
управления. Нужен работающий сервер, разворачивается по `DEPLOY.md`.

**Автономная** — те же карточки, поиск, расчёт расхода, сравнение, избранное
и сбор списка для заявки, но без сервера: каталог лежит одним выгруженным
файлом, корзина — в памяти браузера. Такую сборку можно положить на любой
статический хостинг, в том числе бесплатный.

```bash
node api/src/db/export-static.js      # выгрузить каталог из базы
npm --prefix web run build:standalone # собрать автономную версию
./deploy.sh                           # выложить на GitHub Pages
```

Живой адрес: **https://salamgasanov777-gmm.github.io/habez-pro/**
Исходники: **https://github.com/salamgasanov777-gmm/habez-pro**

Цены и остатки в автономную сборку по умолчанию не выгружаются: настоящих
у нас нет, а выдуманные на публичном сайте завода вводят покупателя
в заблуждение. Когда завод даст прайс — `./deploy.sh --prices`.

### Почему это отдельное приложение, а не вторая версия первого

На телефоне это два разных значка, два разных приложения. Каталог
`hgz-catalog` и `habez-pro` не связаны ничем: разные папки, разные адреса,
разные кеши, разные ключи в хранилище браузера (`hgz-*` против `habezpro.*`).
Работа над первым каталогом продолжается независимо; сломать его отсюда нельзя.

## Запуск за две минуты

Нужен Node.js 22 или новее (`node -v`).

```bash
cd api && npm install && cp .env.example .env && npm run reset && npm start
```

```bash
cd web && npm install && npm run dev
```

Витрина: http://localhost:5173 · API: http://localhost:4000/api/health

`npm run reset` создаёт базу и переносит в неё каталог вместе с **демонстрационными**
ценами. Чтобы работать с настоящими данными завода — без выдуманных цен:

```bash
cd api && npm run migrate && npm run seed
```

Тогда все позиции показываются как «цена по запросу», пока их не проставит
менеджер в панели.

**Учётные записи после `reset`**

| Вход | Пароль | Роль |
|---|---|---|
| admin@habez.local | admin12345 | владелец, полный доступ |
| manager@habez.local | manager12345 | менеджер: заказы, заявки, товары |
| dealer@habez.local | dealer12345 | дилер, видит дилерские цены |

Клиенты входят по коду из SMS. Пока SMS-провайдер не подключён, код
показывается на экране — это режим разработки, в проде так не будет.

**Оплата.** По умолчанию `PAYMENT_PROVIDER=mock`: платёжная страница своя,
кнопка «Оплатить» проводит весь путь до статуса «оплачен». Ключи не нужны.
Боевой режим — `yookassa`, см. `DEPLOY.md`.

## Что честно нужно понимать до запуска

1. **Цен и остатков у нас нет.** Демо-цены помечены как демо и не должны
   попасть на боевой сайт. Настоящий прайс заводит менеджер или он приезжает
   обменом с 1С — обмен нужно писать отдельно и только при содействии IT завода.
2. **Эквайринг, домен, хостинг и SMS оформляются на юрлицо** его сотрудниками.
   Код готов до кнопки «оплатить», дальше — договор и ключи.
3. **152-ФЗ.** В системе хранятся телефоны, адреса и ИНН. Нужны политика
   обработки персональных данных, форма согласия и, возможно, уведомление
   Роскомнадзора. Тексты можно подготовить, но подписывает и отвечает компания.
4. **Дежурство.** Живой системе нужен свой человек на стороне завода: резервные
   копии, разбор сбоев, ответы клиентам.
5. **Безопасность.** Код написан с оглядкой на типовые дыры (см. `docs/SECURITY.md`),
   но перед запуском систему с персональными данными правильно показать
   стороннему специалисту.

Подробности развёртывания — в [DEPLOY.md](DEPLOY.md).
